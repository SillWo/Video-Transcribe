# Локальная обработка демонстраций экрана в Windows

Проверено 14 ноября 2026 года. Условия: Ryzen 7 8845H, около 31 ГБ доступной RAM, Radeon 780M; запись и предварительная обработка локально, в ChatGPT/Gemini передаются только разрешённые пользователем подготовленные материалы. Это исследование документации. Скорость и качество перечисленных OCR/VLM на данном ПК не измерялись; установки не выполнялись, код проекта не менялся.

## Вывод

Самый простой технически обоснованный старт — **OBS → существующий локальный ASR → извлечение изменившихся экранных областей → RapidOCR на ONNX Runtime CPU → локальные структурированные события с кадрами и временем**. PaddleOCR CPU сравнить на одном и том же наборе кадров. Локальную VLM подключать только для неоднозначных визуальных переходов после проверки качества, не назначать ей обязательную обработку каждого кадра.

Windows, Docker/WSL и CUDA не должны быть одновременно обязательными частями этого конвейера. Имеющийся проект уже располагает записью времени, ASR, диаризацией и изолированными обработчиками; визуальную обработку разумно держать отдельно от работающего ASR окружения.

## Три варианта OCR

| Вариант | Что подтверждено | Лицензия и зависимости | Решение |
|---|---|---|---|
| RapidOCR + ONNX Runtime CPU | Локальные модели, ONNX Runtime как основной движок; отдельные multilingual recognizers | RapidOCR Apache-2.0; зарегистрированные OCR модели Apache-2.0; Python, CPU ONNX Runtime, OpenCV и модели | Первый кандидат пилота: не требует GPU, Paddle framework или MSIX |
| PaddleOCR CPU | Windows поддерживается; доступны CPU установка, локальные пути моделей, русский/английский | PaddleOCR Apache-2.0; отдельное окружение PaddlePaddle CPU и OCR модели | Сравнительный вариант, если удобнее официальная модельная цепочка или качество RapidOCR недостаточно |
| Windows.Media.Ocr | Системное OCR, языки и предел размера изображения запрашиваются у устройства | API Windows, не независимый открытый OCR-движок; Microsoft официально требует package identity для desktop | Возможный последующий packaged-helper; не базовая «простая функция Python» |

### RapidOCR

[Официальная инструкция](https://rapidai.github.io/RapidOCRDocs/main/install_usage/rapidocr/install/) рекомендует `rapidocr` вместе с `onnxruntime`; старые отдельные пакеты `rapidocr_onnxruntime`, `rapidocr_openvino`, `rapidocr_paddle` постепенно выводятся из основной разработки. Сам движок начиная с определённых версий устанавливается отдельно, поэтому одного имени OCR-пакета в списке зависимостей недостаточно. [ONNX Runtime](https://onnxruntime.ai/docs/install/) имеет CPU вариант и отдельные GPU варианты; базовую оценку следует проводить на CPU.

[Список моделей RapidOCR](https://rapidai.github.io/RapidOCRDocs/main/en/model_list/) содержит `eslav` и `cyrillic` PP-OCRv5 recognizers в ONNX-формате. Для рабочих экранов русского и английского языка нельзя оставлять случайный recognizer по умолчанию. [Первичный список PaddleOCR](https://www.paddleocr.ai/main/en/version3.x/algorithm/PP-OCRv5/PP-OCRv5_multi_languages.html) прямо указывает русский, белорусский, украинский и английский для `eslav_PP-OCRv5_mobile_rec`; кириллическая модель охватывает ещё больше языков, включая английский. Практический первый выбор для проверки — East Slavic recognizer плюс подходящий текстовый detector; сравнить с отдельным English recognizer на SQL/идентификаторах. Поддержка языка не равна гарантированной точности Jira, таблиц и мелкого кода.

[Заявление о лицензиях](https://rapidai.github.io/RapidOCRDocs/main/model_licenses/) разделяет авторство RapidOCR-кода и PaddleOCR-весов, но распространяет зарегистрированные модели по Apache-2.0. Словари и шрифты перечислены отдельно: при упаковке приложения сохранить сведения о конкретных артефактах и их лицензиях, а не переносить лицензию одного репозитория на любые файлы.

### PaddleOCR CPU

[Официальная инструкция PaddleOCR](https://www.paddleocr.ai/main/en/version3.x/paddlepaddle_installation.html) предусматривает CPU PaddlePaddle; [FAQ официального репозитория](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/FAQ.en.md) подтверждает Windows и локальные каталоги моделей. Это позволяет работать после предварительной загрузки без отправки кадров в API. [Лицензия кода — Apache-2.0](https://github.com/PaddlePaddle/PaddleOCR/blob/main/LICENSE).

Для пилота нужен обычный text detection + recognition, а не вся document parsing/VL платформа. Не включать по инерции поворот документов, распрямление, формулы, большие серверные layout-модели или облачное извлечение. Сравнивать RapidOCR и PaddleOCR на одинаковых моделях и кадрах, иначе разница объясняется не движком, а моделью. Размещение дополнительных зависимостей в отдельном окружении уменьшит риск нарушения текущего ASR.

### Windows OCR

[Microsoft Windows.Media.Ocr](https://learn.microsoft.com/en-us/uwp/api/windows.media.ocr?view=winrt-26100) официально поддерживается для desktop приложений с package identity; страница поясняет MSIX. Поэтому неподдерживаемый обход через случайный PowerShell/Python wrapper нельзя считать надёжной основой продукта. [OcrEngine](https://learn.microsoft.com/en-us/uwp/api/windows.media.ocr.ocrengine?view=winrt-26100) предоставляет `AvailableRecognizerLanguages` и `MaxImageDimension`: доступность русского и ограничения размера нужно получать на конкретной машине. Упакованный вспомогательный процесс возможен как отдельный инженерный вариант, но это дополнительная работа по поставке, а не отсутствие зависимостей.

## Необязательная локальная VLM

[llama.cpp multimodal](https://github.com/ggml-org/llama.cpp/blob/master/docs/multimodal.md) поддерживает локальные изображения/видео через `libmtmd`, projector и серверный интерфейс; в списке есть небольшие SmolVLM и Qwen2.5-VL-3B. [Инструкция сборки](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md) описывает Windows Vulkan, а [лицензия движка](https://github.com/ggml-org/llama.cpp/blob/master/LICENSE) — MIT. Лицензию выбранных весов нужно проверять отдельно. Наличие Vulkan в движке **не подтверждает** работу конкретной модели с projector на Radeon 780M и тем более её скорость/точность.

Кандидатное применение: описать 2–4 соседних ключевых кадра с OCR и коротким фрагментом речи, затем предложить переход вида «открыта карточка → изменён статус». Такие описания — производные гипотезы с привязкой к доказательствам, а не источник истинных SQL-запросов или действий. Любой вычислительный бюджет VLM считать отдельно: число кадров × измеренное среднее/95-й перцентиль времени на кадр. Не обещать, что 2-часовое видео обработается в реальном времени.

## Как не потерять маленькое изменение интерфейса

[PySceneDetect](https://www.scenedetect.com/docs/latest/api/detectors.html) определяет ContentDetector как пороговое изменение пикселей/HSV, AdaptiveDetector — как относительное изменение с rolling average. Это инструменты границ сцен. Из их принципа следует: появление маленького меню или замена одного значения на большом статичном экране могут не дать достаточного общего сигнала. Использовать scene cuts как один из сигналов, не единственный.

Предлагаемый алгоритм для проверки:

1. Сохранять исходную полноценную запись OBS без уменьшения разрешения текста; извлекать кадры с исходными presentation timestamps. Понижение разрешения допустимо для детектора изменений, но не для окончательного OCR мелких символов.
2. Разделить изображение на области: демонстрация, участники, элементы Jitsi. Изменение лица/микрофонной рамки не должно постоянно запускать полный OCR демонстрации.
3. Сравнивать локальные плитки/области, а не только общий хеш. Изменение маленького Jira-статуса, SQL-значения или меню должно запускать обработку соответствующей области, даже когда 99% экрана остались прежними.
4. Проверить начальную настройку 2–4 дешёвых сравнений в секунду, объединение коротких всплесков и OCR устойчивого состояния после изменения. Сохранять предыдущее, переходное и стабилизировавшееся состояние; периодический контрольный кадр, например каждые 5 секунд, страхует ошибки детектора. Это параметры эксперимента, не измеренная оптимальная конфигурация.
5. Повторно не распознавать неизменившийся текст; хранить его интервал видимости. Для таблиц сохранять координаты строк/столбцов и общий кадр, иначе OCR-список легко смешивает значение и заголовок.
6. Для жалобы «пропущен важный клик» возвращаться к исходному временному окну и переизвлекать кадры плотнее. Ни один редкий sampling не гарантирует восстановление всех коротких всплывающих подсказок.

При сравнении в 4 fps двухчасовая запись даёт 28 800 дешёвых сравнений. Это **не означает 28 800 обязательных OCR/VLM-запросов**: итоговый набор зависит от реального изменения рабочих областей. Измерять и число кандидатов, и сохранённых состояний, и очередь OCR.

## Что нельзя получить из такого видео

- ОС на компьютере зрителя не получает DOM, SQL buffer, настоящие события мыши или clipboard удалённого демонстратора. Jitsi показывает видеопиксели. Локальный click-hook видит клики самого зрителя, что нельзя выдавать за действия собеседника.
- Видимый курсор и смена изображения могут позволить выдвинуть гипотезу о клике; отсутствие cursor/click telemetry не позволяет гарантировать способ запуска команды. Возможны клавиатура, горячая клавиша или действие вне кадра.
- DBeaver показывает только видимые строки, столбцы и текст. Скрытые вкладки, обрезанные SQL, значения за горизонтальным скроллом и неоткрытые данные не восстанавливаются достоверно.
- Для вопроса «что сказал конкретный человек» нужны проверенные имена участников и сопоставление с говорящими. Номер кластера диаризации не является личностью; звук браузера обычно уже смешивает удалённых участников.
- Jira, чаты и код содержат точные идентификаторы. Автоисправленную моделью версию хранить отдельно от OCR/ASR, не исправлять незаметно `O/0`, `l/1`, номера задач и даты по догадке.

## Проверяемый пилот на двухчасовой записи

Сначала 40–60 вручную отобранных кадров для сравнения двух OCR, затем один полный 2-часовой screencast Jira/DBeaver/чатов. Если нельзя загрузить кадры в облако, вся проверка извлечения и её эталон остаются локальными.

Критерии для согласования с пользователем, не заявления уже достигнутого качества:

- Из 30 заранее размеченных значимых визуальных переходов обнаружить не менее 27; все пропуски показать отдельно. Включить мелкую смену статуса, короткое меню, смену вкладки, прокрутку, SQL-result и чат.
- На 100 вручную проверенных видимых значениях точное совпадение для Jira-ID/имён/дат/чисел не менее 95%; сомнительные значения помечены. Средняя OCR confidence не заменяет эту проверку.
- Из показанной процедуры в 15 шагов получить правильный порядок и доказательство каждого существенного шага; пропущенные действия отмечены, не достроены. Проверить отдельно верное название выбранного пункта и вывод о том, что действие действительно состоялось.
- 10 вопросов «что сказал человек о задаче/сроке» отвечаются со временем и подтверждённым говорящим; 10 визуальных вопросов — с исходным кадром; 5 заведомо отсутствующих фактов не выдумываются.
- Записать длительность декодирования, ASR, OCR, индексации, опциональной VLM, пиковую RAM, объём архива и число кадров. Два OCR не гонять одновременно с ASR для первого честного замера.
- Целевой первоначальный предел: вся 2-часовая запись обрабатывается не дольше 2 часов без VLM, с пиком памяти не выше согласованного бюджета и без повреждения текущей встречи. Это критерий feasibility, не обещание производительности.
- Для максимального потока до 12 часов записей в сутки одного коэффициента 1× недостаточно при коротком окне ночной обработки. Например, при 8 доступных часах нужно суммарно не менее 1.5× реального времени. Очередь, перенос между днями и фактический средний поток оценить по недельному пилоту.
- После загрузки моделей подготовка должна завершаться с отключёнными облачными API; облаку передаётся только явно выбранный пакет результатов. Если пакет включает кадры, их разрешённость нужно определить отдельно: слово «обработанный» не делает изображение автоматически обезличенным.

Пилот должен ответить, достаточно ли OCR + временной шкалы для текста и процедур. Только если визуальные факты систематически теряются при хорошем OCR, добавлять локальную VLM или иной специализированный анализ. Бюджет API не следует расходовать на обязательный полный просмотр каждой ежедневной записи.
