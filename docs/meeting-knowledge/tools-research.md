# Инструменты для памяти рабочих созвонов

Проверено 14 ноября 2026 года. Исследование по первичным публичным источникам; приложения не устанавливались, реальная запись и качество поиска не проверялись. Ни один продукт ниже не объявлен готовым решением всех требований без проверки на записях пользователя.

## Платформа meet.egovm.ru

Прямой HTTP GET [публичной стартовой страницы](https://meet.egovm.ru/) вернул 200. В HTML присутствуют `JitsiMeetJS`, `lib-jitsi-meet.min.js`, `APP_NAME: 'Jitsi Meet'` и конфигурация Jitsi. Следовательно, это установка Jitsi Meet, а не предположение по названию домена. В публичной клиентской конфигурации выставлены `recordingService.enabled: true`, `localRecording.disable: false`, `transcription.enabled: true`.

Эти флаги **не подтверждают** наличие работающего сервиса записи, его свободных ресурсов и прав пользователя. Сначала следует проверить доступные команды записи в обычном рабочем интерфейсе. Комнаты не открывались, авторизация не использовалась.

Официальный [Jibri](https://github.com/jitsi/jibri) записывает конференции Jitsi через Chrome и FFmpeg; требует настройки инфраструктуры Jitsi и отдельного сервера/VM. Это потенциальный путь при участии администратора сервиса, не локальная утилита, которую участник может подключить к чужому серверу самостоятельно.

## Сравнение шести кандидатов

| Кандидат | Захват | Зрительный контекст | Доступ агента | Главный предел |
|---|---|---|---|---|
| OBS Studio | Полноценная видеозапись окна/экрана и выбранных аудиоисточников в Windows | Сохраняет исходные пиксели, но не индексирует их | Нужен последующий обработчик и поиск | Надёжный слой записи, не база знаний |
| Screenpipe | Запись экрана, микрофона и системного звука, история работы | Accessibility/OCR, кадры, временные привязки | Готовые локальные REST API и MCP | Ближайший готовый кандидат, но текущая лицензия коммерческая; требуется проверка демонстраций экрана |
| Meetily Community/Pro | Микрофон + системный звук, локальная транскрибация | Визуальный поиск по демонстрации не подтверждён | В текущем описании API/MCP/CLI относятся к Pro | Закрывает аудиозаметки, не весь мультимодальный архив |
| Anarlog, ранее Hyprnote | Локальный блокнот созвонов, запись/транскрибация | Полноценный видеоиндекс не подтверждён | CLI/MCP присутствуют | Windows требует отдельного локального STT-сервера или облачного провайдера |
| HKUDS VideoRAG / Vimo | Импорт существующих видео | Мультимодальный поиск по нескольким видео | Исследовательский backend; готовая интеграция агента потребует проверки/доработки | Не готовый Windows installer; аппаратные и лицензионные ограничения |
| NotebookLM / Gemini Notebook | Импорт источников и аудио | YouTube импортируется как транскрипт; не считать визуальным пониманием видео | Интерфейс работы с источниками, не локальный универсальный архив | Полезен для текста/конспектов, но не закрывает требование видеть экран |

## OBS: оптимальный независимый слой записи

[OBS Studio](https://obsproject.com/) — бесплатное открытое приложение для Windows, macOS и Linux, захватывает окно/экран и аудио. Официальная [инструкция по захвату аудио приложения](https://obsproject.com/kb/application-audio-capture-guide) подтверждает поддержку Windows 10 2004+ и Windows 11; можно отделить звук браузера от прочих приложений. [Раздельные звуковые дорожки](https://obsproject.com/kb/multiple-audio-track-recording-guide) позволяют сохранить микрофон отдельно от собеседников и общий микс для обычного просмотра.

Предлагаемая конфигурация для проверки: окно Jitsi/браузера; дорожка 1 — микс; дорожка 2 — микрофон; дорожка 3 — аудио браузера. Это разделение «я/удалённая сторона», а не отдельная дорожка для каждого удалённого участника. Другие звуки того же процесса браузера также могут попасть в запись, поэтому полезно выделить созвонам отдельный браузер. Последнее — проектная рекомендация, а не проверенное свойство конкретной конфигурации пользователя.

При захвате окна сохраняется показанный пользователю видеоряд, а не недоступные ему вкладки, исходные файлы презентаций и документы собеседника. Смена окна, сворачивание, полноэкранная демонстрация и всплывающие диалоги должны входить в проверку записи.

## Screenpipe: первый кандидат для короткого продуктового пилота

Текущий [официальный README](https://github.com/screenpipe/screenpipe) заявляет готовые сборки Windows/macOS/Linux, локальное хранение, извлечение текста accessibility с OCR как резервом, запись аудио и подключение агентов. Он прямо называет проект source-available. Это существенно: **не называть текущий Screenpipe MIT-проектом**.

[Текущая лицензия](https://github.com/screenpipe/screenpipe/blob/main/LICENSE.md) называется Screenpipe Commercial License. Она различает собственные сборки и официальные дистрибутивы; рабочее коммерческое использование собранного исходного кода требует коммерческой лицензии, а официальные сборки подчиняются условиям продукта/подписки. Старые версии, выпущенные под MIT, сохраняют свою лицензию. Для выбора инструмента рабочих созвонов нужны актуальные условия конкретной сборки, а не совет «скомпилировать бесплатно» из старого поста.

[Официальная страница поиска](https://docs.screenpipe.com/search-screen-history) описывает событийный захват, accessibility/OCR, SQLite и локальный `/search`. Она уточняет: текстовый запрос API сам по себе не обещает векторный семантический поиск. Значит, «найди обсуждение риска миграции» может потребовать нескольких поисков и синтеза агентом.

[MCP](https://docs.screenpipe.com/mcp-server) даёт поиск по экрану/аудио/времени/приложению, получение кадров и экспорт временного диапазона видео. [Meeting intelligence](https://docs.screenpipe.com/meeting-intelligence) связывает запись встречи, расшифровку, экранный контекст, заметки и временные якоря. Это документированная функциональность, не мой результат испытаний.

Ключевая неопределённость для Jitsi: демонстрация собеседника — видеопиксели внутри браузера. Accessibility-дерево страницы не равно тексту удалённого экрана. Нужны удачный OCR и достаточно частый захват. Событийная запись может упустить короткий слайд/меню/анимацию, поэтому полноценную исходную запись OBS полезно оставить хотя бы на пилоте. [Changelog в официальном репозитории](https://github.com/screenpipe/screenpipe/blob/main/docs/mintlify/docs-mintlify-mig-tmp/changelog.mdx) описывает режим HD и изменения захвата; доступность соответствующего поведения нужно проверять в установленном релизе, а не выводить из main.

## Аудиоблокноты: полезны, но не заменяют зрительный архив

[Meetily](https://github.com/Zackriya-Solutions/meetily) предлагает MIT Community, Windows installer, локальные Whisper/Parakeet, одновременный микрофон и системное аудио. Стандартный Windows пакет использует Vulkan; CUDA требует подходящей сборки. Текущий README относит API, MCP, CLI, webhooks, расширенные экспорты и идентификацию говорящих к Pro. Это хороший кандидат, если главная боль — ручной перенос аудиорасшифровок. Видеопонимание демонстрации экрана в проверенном описании не заявлено. У пользователя уже есть серьёзный локальный ASR, поэтому замена на Meetily оправдана только реальным выигрышем записи и доступа агента.

Старый [Hyprnote](https://github.com/fastrepl/hyprnote) перенаправляет на **Anarlog**. Официальный README говорит о MIT Community, коммерческих enterprise-компонентах, Windows/macOS/Linux, Markdown, CLI/MCP. [Документация моделей](https://docs.anarlog.so/models-and-providers) различает транскрибацию и модель для ответов; поиск встреч использует локальный Tantivy, не LLM и не embeddings. [Первичный материал разработчика об офлайн-режиме](https://anarlog.so/blog/local-ai-meeting-notes/) уточняет: встроенные локальные речевые модели требуют поддерживаемый Apple Silicon Mac; для Windows нужен отдельный Deepgram-совместимый локальный сервер или облачная речь. Поэтому для данного Windows-ПК это не очевидно более простой путь, чем имеющийся Video-Transcribe. Полноценного видеоиндекса проверенные источники не подтверждают.

## VideoRAG/Vimo: подходящая идея, сложная стартовая база

[VideoRAG](https://github.com/HKUDS/VideoRAG) описывает графовый и мультимодальный поиск по длинным и нескольким видео. Однако основной README одновременно рекламирует кроссплатформенность и помечает готовую загрузку Vimo как Coming Soon, сначала для Apple Silicon; для старта предлагается исходный Python backend и Electron frontend. Указанный авторами аппаратный пример — RTX 3090 24GB. Нельзя переносить обещания на Radeon 780M.

[LICENSE проекта](https://github.com/HKUDS/VideoRAG/blob/main/LICENSE) явно разделяет MIT архитектуры и ограничения текущих интегрированных моделей: ImageBind имеет NonCommercial-условия; использование текущей реализации как есть помечено NonCommercial. Для рабочих задач это кандидат на изучение подхода или замену компонентов, а не готовый коммерчески свободный стек. Из-за этих двух ограничений не рекомендую начинать пилот с установки Vimo.

## NotebookLM: полезный текстовый спутник

Текущая [официальная справка Google](https://support.google.com/gemininotebook/answer/16215270?hl=en) под названием Gemini Notebook описывает загрузку локального аудио как транскрибацию в текст, а YouTube — как импорт только текста субтитров. MP4 встречается среди форматов аудиоимпорта, что не доказывает понимания видеокадров. Поэтому этот инструмент можно рассматривать для ответа по подготовленным текстам, документам и отчётам со ссылками на источники. Нельзя обещать, что загрузка ролика или YouTube-ссылки даст знание его экранного содержимого.

## Предложение для пилота и граница готовой автоматизации

Два варианта для выбора после уточнения требований:

1. **Минимум разработки:** пилот Screenpipe на разрешённой тестовой встрече + исходная запись OBS. Проверить именно OCR удалённой демонстрации, русский текст, доступ MCP, поиск между встречами и лицензионную стоимость рабочего использования. Если это проходит приёмку, собственная база может не понадобиться.
2. **Контролируемый архив на открытых компонентах:** OBS → папка входящих записей → имеющийся Video-Transcribe → выделение сцен/кадров и OCR → выбранная мультимодальная модель → индекс аудиофрагментов и визуальных событий с общей шкалой времени → доступ агента через инструменты поиска/кадров/клипов. Запись и ASR уже имеют основы; связка видеопонимания, доказательств, поиска и агентского интерфейса потребует разработки. Обычный summary.txt недостаточен.

В предлагаемом архиве оригинал следует сохранять неизменным; поисковый индекс должен хранить `meeting_id`, `start/end`, точный текст/OCR, кадры и ссылку на исходник. Выводы модели и исправления транскрипции должны быть отдельным слоем, чтобы можно было отличить наблюдение от интерпретации. Визуальный поисковый результат должен позволять агенту вернуться к кадру или короткому исходному клипу. Это проектное предложение, не готовая интеграция перечисленных продуктов.

## Критерии приёмки

На одной разрешённой 30–60-минутной встрече и двух предыдущих записях:

- Записаны пользователь и удалённые участники без эха, пропусков и систематического рассинхрона; перезапуск аудиоустройства не оставляет незаметно пустую дорожку.
- Найдены 5 заранее отмеченных фактов, сказанных вслух, и 5 фактов, показанных только на экране: число в таблице, URL, название поля, ошибка, фрагмент кода.
- Для каждого ответа есть правильная встреча, время и открываемый исходный кадр/клип. Нет выдуманных имён говорящих и точных чисел из нечитаемого текста.
- Найдено изменение решения между двумя встречами с отдельными ссылками на обе версии.
- На вопрос о отсутствующем факте агент сообщает, что подтверждение не найдено, вместо достраивания ответа.
- Измерены объём на час, время обработки, расходы API и нагрузка во время браузерного звонка на конкретном ПК пользователя.
- Данные и промежуточные модели настроены на диск D; архив не зависит от краткоживущего облачного upload или исчезнувшего чата.

Итог исследования: Screenpipe стоит проверить как ближайшее готовое решение, если устраивает текущая лицензия; OBS — самый независимый слой исходной записи; имеющийся ASR разумно сохранять в собственном конвейере. Аудиоблокноты без видеослоя и исследовательский VideoRAG не закрывают весь запрос автоматически.
